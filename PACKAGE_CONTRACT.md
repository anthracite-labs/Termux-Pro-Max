# Termux Pro — Package and Runtime Contract

**Status:** candidate normative interface implemented by the builder and Java Android consumer; host conformance passes. **Android package loading remains unverified.**
**Source:** requirements derived from the attached Termux Pro Architecture Report; Android/Termux-specific changes are research-backed proposals as recorded in [ARCHITECTURE.md](ARCHITECTURE.md).  
**Reference registry:** [README.md](README.md#evidence-register).

## 1. One contract, two consumers

| Plain language | Technical meaning |
|---|---|
| The factory and app must agree on what is in a package. | Builder MUST publish the schema and app MUST validate it before installing. |
| All packages belong to one Android app. | Every target artifact uses the chosen `APP_ID`, its canonical `$PREFIX`, and a compatible NDK API/ABI configuration. |
| Each command gets one front door. | Each exported command has exactly one selected active provider at installation time; no runtime search through arbitrary candidate paths. |
| Bash is just another package. | Shell selection is configuration; executable dispatch is not implemented inside Bash. |

Normative words: **MUST**, **SHOULD**, **MAY** indicate required behavior, recommended behavior, optional behavior. Unverified mechanics remain *candidates* regardless of MUST statements.

## 2. Global invariants

1. Release ABI is `arm64-v8a` for MVP; other ABIs require a new validated contract version.
2. Application ID and canonical private `$PREFIX` are **immutable build inputs** per app identity; NEVER bake `com.termux` paths into Termux Pro packages. [S8][S18]
3. Prefix layout: `$PREFIX/{bin,lib,libexec/tp-real,share,etc,var/lib/termux-pro,tmp}`; user home is outside `$PREFIX` under app-private `files/home`.
4. Native commands that the chosen launcher routes through Bionic `linker64` MUST be compatible **dynamically linked** Android ELF AArch64 binaries, with required dependencies available. Static and foreign-ABI executables are rejected for this route. [S1][S2][S16]
5. Builder MUST declare every exported command, interpreter and executable helper. Installed command paths are generated by the installer and never inferred from an arbitrary filename search.
6. Source provenance and content hashes MUST be present; a hash does not prove a program is safe. [S11]
7. The app MUST NOT invoke package-provided install scripts as privileged Android app setup steps; installation is extraction plus validated metadata and explicitly approved transformations. Runtime post-install scripts, if ever introduced, require a separate security decision.
8. The app MUST NOT silently modify its own installed APK or extracted protected native library directory.

## 3. Concrete runtime paths (candidate)

```text
Android Context.getFilesDir() = <files>       # discovered at runtime
HOME       = <files>/home
PREFIX     = <files>/usr
PATH       = <files>/usr/bin : reviewed Android system entries
TMPDIR     = <files>/usr/tmp

<files>/usr/bin/gh             -> protected launcher (managed entry)
<files>/usr/libexec/tp-real/gh    actual dynamically linked ELF
<files>/usr/lib/                required shared objects
<files>/usr/share/              package assets
<files>/usr/var/lib/termux-pro/ package manifests / ownership index
```

**Important:** The command symlink from writable `$PREFIX/bin` to the protected launcher is a **design hypothesis**, not an Android guarantee. It must pass [VERIFICATION.md](VERIFICATION.md) gate E1. The package contract's logical command names survive if the execution mechanism is replaced; do not require package producers to embed launcher implementation details.

The `libexec/tp-real/<command>` flat staging convention is intentionally minimal. It introduces a **collision risk for helper executables**, so non-exported helpers should be installed at their upstream-compatible package-specific paths (e.g. `libexec/git-core/`) with their path rules recorded in the recipe. Only exported command targets use the managed flat command map. Complex package data remains under `share` or other documented subdirectories.

## 4. Minimal package manifest (proposed v1)

```json
{
  "schema": 1,
  "id": "gh",
  "version": "<pinned-version>",
  "revision": 1,
  "abi": "arm64-v8a",
  "min_android_api": 30,
  "app_id": "<fixed-application-id>",
  "prefix": "<build-time-absolute-prefix>",
  "source": {
    "upstream": "<official-source-url>",
    "revision": "<immutable-tag-or-commit>",
    "sha256": "<verified-source-digest>"
  },
  "dependencies": ["git"],
  "commands": [
    {"name": "gh", "kind": "elf", "target": "libexec/tp-real/gh"}
  ],
  "files": [
    {"path": "libexec/tp-real/gh", "sha256": "<file-digest>", "mode": "0644"}
  ],
  "licenses": ["<SPDX-identifier>"],
  "build_id": "<build-attestation-id>"
}
```

This JSON is a **schema example, not real package metadata**. Real versions, digest values and paths are supplied by the builder; the archive SHA-256 MUST live in an external signed release index or other non-self-referential envelope rather than in its own payload manifest. During implementation, define precisely which files are covered by each digest; a self-hashing archive is invalid. The `build_id` above is an identifier, not an integrity digest.

**Required fields:** `schema`, `id`, `version`, `revision`, `abi`, `min_android_api`, `app_id`, `prefix`, `source`, `dependencies`, `commands`, `files`, `licenses`. Unknown required schema versions MUST fail rather than be guessed. Authentication/signature material MUST bind the manifest and full payload. In MVP, a release index can sign the archive hash; choose one signature scheme before enabling remote package delivery.

## 5. Exported command semantics

- `name`: ASCII command identifier without `/`, `..`, control characters or whitespace; must be unique among installed active providers.
- `kind=elf`: points to an ELF within the allowed package prefix, and the selected launcher/loader starts it. Not a shell script with a `.so` extension.
- `kind=script`: explicit interpreter reference and script target, both registered and known at package-build time. No assumption that kernel shebang execution of writable scripts will work.
- Command-specific helper executables not invoked directly via PATH MUST have explicit supported invocation rules. `gh -> git`, `git -> ssh` are mandatory integration paths.
- Unknown commands return a normal command-not-found error; missing package target gives a clear install-integrity error; never fall through to executing arbitrary files by guessed absolute path.
- Arguments are preserved exactly as separate strings; no shell interpolation, no rejoining into one command string; environment and inherited file descriptors remain under normal process rules.
- Launch result: preserve exit code, signal and job-control effects. Launcher must avoid adding a resident process to every command invocation if an `exec` chain suffices.
- Multiple potential providers/paths are resolved at **install time** with explicit priority or user selection; runtime sees one committed target.

## 6. ELF and dynamic-library rules

- Required: ELF64 little-endian AArch64, appropriate machine/type/interpreter and dynamic segment for the tested Bionic explicit-linker route, and 16 KB-compatible load segment alignment. [S9][S16]
- Inspect `DT_NEEDED` and validate dependency presence and namespace/loadability on the target API; `readelf` success on Linux is not proof Android loader succeeds.
- Avoid broad global `LD_LIBRARY_PATH` when a package can use controlled RUNPATH / `$ORIGIN` layout. Verify Android linker behavior for all selected APIs.
- Binary `argv[0]` and executable path visibility can differ under explicit linker invocation; test packages using executable path discovery (Go, Python, Node, Git helpers).
- Shell scripts, shebang chains, tools such as `env`, scripts launched by subprocess libraries, and programs with hardcoded `/bin/sh` need concrete tests and targeted patch recipes.
- Unsupported binaries are rejected with diagnostic evidence; do not attempt to circumvent kernel restrictions using custom ELF memory loaders.

## 7. Installer contract (not a full package manager)

1. Confirm the package is from an approved delivery route for the **chosen distribution channel**. A Google Play release MUST NOT assume externally fetched executable packages are permitted. [S13][S14]
2. Validate envelope signature/trusted index when configured, source provenance, manifest schema, `APP_ID`, ABI/API, prefix and dependency constraints.
3. Validate entire archive before extraction: path traversal, absolute paths, duplicate normalized names, unsafe hardlinks/symlinks, decompression bombs, device/special files and excessive sizes.
4. Extract into a private staging directory under the app's control; refuse files outside allowed `$PREFIX` roots.
5. Validate file hashes, modes and ELF/script checks. Build command ownership index and detect conflicting file paths.
6. Stage new command entries, test their targets, then switch to a complete committed package state with rollback metadata. Atomic rename works only within a filesystem and does not automatically make multi-file installs atomic; use a transaction journal and recovery path.
7. On crash/interruption, recover last valid committed state; never leave a half-installed command that points to missing or unverified files.
8. Uninstall only files owned by the package and not owned/shared by another; never delete arbitrary directories based on user strings.

Package data is mutable to programs under the same app UID. Signed archives protect delivery and updates; they do not make installed files immutable. Do not imply per-package sandboxing.

## 8. Builder / app responsibilities

| Owner | MUST do | MUST NOT do |
|---|---|---|
| Builder | Pin sources, build dependency closure, apply reviewed patches, stage one prefix, emit manifest, run static and Android tests | Download opaque prebuilt Android package dependencies for release; claim tests not run |
| App | Verify imports, stage safely, manage command entries, create PTYs, start supported processes, report failures | Guess paths; silently run incompatible binaries; execute install scripts as privileged setup |
| Package | Honor prefix and command contract; use supported child launch patterns; carry assets/dependencies | Rely on arbitrary absolute direct `execve` of writable binaries |

## 9. Examples and anti-examples

| Example | Expected result |
|---|---|
| `gh auth login` | Bash finds managed `gh` entry; launcher invokes compatible `gh`. |
| GH internally runs `git` via PATH | Managed Git entry receives invocation and starts the Git ELF. |
| Git executes `/data/.../usr/libexec/tp-real/ssh` directly | Unsupported until patched; bypasses managed entry. |
| Python `subprocess.run(["git", "--version"])` | Must succeed via managed PATH in integration test. |
| `/data/.../usr/bin/foo` is an unregistered arbitrary ELF | Must fail closed; no directory-wide arbitrary dispatcher. |
| Statically linked Go target | Not supported by the explicit dynamic linker route; builder must produce compatible alternative or exclude it. |
| Malicious archive path `../../home/.ssh/...` | Rejected before extraction. |

## 10. Acceptance criteria

- [ ] Contract version is frozen, app and builder use the **same** schema fixture and validator test vectors.
- [ ] Package metadata identifies exact source and dependency versions; every payload file is accounted for.
- [ ] Import rejects wrong ABI/prefix/schema, signature failures, path escapes, collisions and incomplete archives.
- [ ] Native executable, shared dependency, script, helper and nested subprocess have explicit positive and negative tests.
- [ ] A package archive built locally can be imported unchanged into the app on an emulator/device.
- [ ] The validated mechanism covers `bash -> gh -> git -> ssh`; if not, architecture decision is reopened.

**Verification record:** No acceptance test is claimed passed at document publication. See [VERIFICATION.md](VERIFICATION.md) and the dependency order in [IMPLEMENTATION_PLAN.md](IMPLEMENTATION_PLAN.md).

## 11. Candidate v1 carrier (T07 implementation)

The concrete candidate carrier is ZIP (`.tpkg`), implemented in
`shared/contract.py`; its identity inputs are `shared/target.json`. This chooses
the archive format that the original builder specification intentionally left
internal. No runtime resolver or package-manager DSL is introduced.

A package contains exactly `manifest.json` plus `payload/<manifest file path>`
for each inventory entry. Every payload entry is a regular file (no archive
symlinks/hardlinks/special files or implicit directories), with mode 0644 or 0755. The seekable ZIP carrier
uses matching local/central headers, no comments, data descriptors, split archives
or ZIP64; flags are zero or UTF-8 only. The Android consumer verifies local header
names/sizes/CRC, contiguous non-overlapping entries, and bounded decompression.
Native exported targets remain under `libexec/tp-real/`. Host builds resolve
reviewed in-prefix library alias symlinks to regular copies; the Android installer
alone generates managed command links after ownership validation. Development
headers/static archives/pkg-config files are build sysroot inputs, not runtime
payload. Runtime roots are lib, libexec, share and etc. Command kind `script`
remains reserved and is rejected in this first native-only consumer.

JSON duplicate keys, noncanonical/traversing paths, duplicate/undeclared entries,
wrong identity/ABI/prefix/schema/API, wrong hashes/modes, unsupported ELF and
missing declared/DT_NEEDED dependencies are rejected. Limits are 20,000 entries,
512 MiB total uncompressed bytes and 256 MiB per file. ELF load segments must be
16 KB aligned/congruent; host inspection does not prove loading on a 16 KB device.
The source `build_id` is a commit plus `+dirty` when necessary; a separate
`build_inputs_sha256` binds actual lock/recipe/patch/contract input bytes. Optional
build/provenance fields may extend schema 1 without changing required semantics.

`build.sh bootstrap` emits `bootstrap.zip`, with `index.json` and unchanged
`packages/*.tpkg` archives. The index lists each archive's path/id/SHA-256 and the
shared app/ABI/prefix/API identity. The external `bootstrap.sha256` covers the
whole bootstrap archive. Each nested archive hash binds its manifest and payload;
no archive or manifest claims to hash itself. A bundled APK signs the complete
bootstrap and its expected digest through normal Android APK signing. Remote
package signatures/delivery are not enabled by this choice. Play release and
external imports remain gated.
